호출자 주도 저장

실제 서버 사용 코드에서 얻은 기준 사용감만 전이

서로 다른 세대의 ASP.NET·EF Core 서버 호출부를 비교했다. 구현 구조를 복제하지 않고, 여러 프로젝트에서 반복해서 나타난 사용 습관과 병목만 UnityOdb의 판단 근거로 삼는다.

반복된 실사용 UnityOdb에 가져올 것 가져오지 않을 것
타입이 잡힌 Context와 엔터티별 진입점 GameOdbContext.Items 같은 발견 가능한 typed set 수백 개 mapper를 모은 거대 service locator

요청 범위 Context 수명과 service 경계 가져오지 않음 필요하다면 ODB 밖에서 호출 순서와 복구 정책 구성

EF의 DbContext는 짧은 unit of work지만 OdbContext는 활성 데이터와 인덱스를 소유하는 장수명 데이터베이스다. 변경은 Dictionary처럼 즉시 반영되며 SaveChanges, transaction, 격리 수준, write batch를 제공하지 않는다.

실제 호출부에서는 임의 LINQ보다 도메인 이름을 가진 조회가 훨씬 자주 반복됐다. Core는 typed set과 index view를 제공하고, 게임별 FindAllByOwnerId 같은 facade는 호출자가 작고 모듈식으로 구성한다.

런타임 모델

선언, 조회, 변경, 메모리 배치

사전 선언 모델 Context별 1회 구성

General하다는 의미는 런타임에 임의 타입을 자동 추론한다는 뜻이 아니다. 각 프로젝트가 자기 Context에서 테이블과 인덱스를 명시할 수 있다는 뜻이다. 

public sealed class GameOdbContext : OdbContext
{
    public OdbSet<Item, ItemId> Items => GetSet<Item, ItemId>();

    protected override void OnModelCreating(OdbModelBuilder modelBuilder)
    {
        modelBuilder.SetSchemaVersion(3);
        modelBuilder.AddEntity<Item, ItemId>("Item", item => item.Id)
            .SetCapacityHint(8192)
            .AddIndex(item => item.OwnerId)
            .AddUniqueIndex(item => item.Code, StringComparer.Ordinal);
    }
}

Context 모델은 최초 접근 때 한 번 검증·동결하며 선언된 모든 Set과 Index를 함께 생성한다. Definition과 runtime Index 타입은 내부 구현이므로 호출자가 보관하지 않는다.

  • 논리적으로 하나여야 하는 값은 단건 조회 관례가 아니라 AddUniqueIndex로 강제한다.
  • Secondary index selector는 읽을 수 있는 직접 property만 받는다. Primary key selector는 일반 함수로 선언한다.
  • 기본 XML·JSON이 지원하지 않는 값이나 별도 포맷은 사용자 정의 importer·exporter에서 처리한다.
  • Context는 typed facade로 유지하고 모델 선언은 일반 메서드나 작은 configuration module로 분리할 수 있다.

조회와 인덱스 LINQ 재구현 안 함

.NET의 LINQ 연산을 다시 만들지 않는다. OdbSet에 표준 LINQ를 바로 적용하면 전체 Set을 순회한다. 고유 값은 TryFindBy로 한 건을 찾고, 비고유 값은 FindBy로 bucket view를 얻은 뒤 표준 LINQ를 적용한다. 

if (db.Items.TryFind(itemId, out var item))
    Use(item);

if (db.Items.TryFindBy(item => item.Code, itemCode, out var codedItem))
    Use(codedItem);

var ownedItems = db.Items.FindBy(item => item.OwnerId, ownerId);

var visibleItems = ownedItems
    .Where(item => item.IsVisible)
    .OrderByDescending(item => item.Level);
인덱스 대표 구조 용도
Primary Key → Entity TryFind, 식별자 조회
Unique Hash IndexKey → Entity 계정 ID 등 고유 보조 키
Hash IndexKey → Entity bucket Owner, Category 등 equality 조건
Composite Hash (Key A, Key B, ...) → Entity bucket Owner + DataKey 등 반복되는 다중 equality 조건
Ordered 정렬 Key → Entity bucket 범위 검색과 정렬 순회

제한된 IQueryable provider와 prepared query는 직접 인덱스 API의 정확성·성능이 확인된 뒤 선택적으로 추가한다. 지원하지 않는 표현식을 몰래 전체 순회시키지 않고 진단하거나 명시적으로 AsEnumerable() 경계를 요구한다.

호출자는 definition field나 runtime Index property를 만들지 않는다. Selector 식은 등록된 property를 찾는 데만 쓰고, 실제 데이터 조회는 해당 Dictionary·bucket에서 수행한다. 식 트리 생성 비용까지 없애야 하는 반복 hot path는 benchmark 뒤 prepared query나 source generation을 별도 검토한다.
변경과 인덱스 정합성 Change tracker 없음

저장된 엔터티 인스턴스는 불변으로 취급한다. 조회 결과를 직접 바꾸지 않고 새 인스턴스를 만든 뒤 Replace해야 한다. 이전 index key를 읽어 primary·secondary index를 함께 갱신하기 위한 계약이며 transaction이나 예외 rollback을 제공하기 위한 장치는 아니다. 

if (db.Items.TryFind(itemId, out var current))
    db.Items.Replace(itemId, new Item(current.Id, nextOwnerId, nextLevel));

  • Add·TryAdd, Replace·TryReplace, Remove를 기본 변경 API로 둔다.
  • 엔터티 defensive copy는 만들지 않으며 저장된 인스턴스 전체를 불변으로 취급한다.
  • Primary key 변경은 Replace에서도 금지한다.
  • ValidateIndexes는 primary·secondary key drift를 진단한다.
  • 성공한 단일 변경은 primary map과 index에 즉시 반영하며 별도 SaveChanges를 요구하지 않는다.
  • 여러 행 transaction과 rollback은 범위 밖이며 예상 밖 예외가 발생한 Context는 호출자가 폐기한다.
  • 범용 Upsert는 실제 호출 사례가 생기기 전에는 public API에 넣지 않는다.
OdbContext는 단일 스레드 전용이다. query·mutation·initialize·export에는 lock, 재진입 감지, 동시 접근 방어를 제공하지 않으며 호출자가 같은 스레드에서 순서대로 실행한다.
Export는 호출자가 건넨 Stream의 현재 위치부터 기록한다. 파일 교체나 Cloud 게시를 원자적으로 확정하는 작업은 호출자 저장 계층의 책임이며, export 실패가 현재 메모리 상태를 되돌리지는 않는다.
메모리와 할당 전략 Resident memory 허용

메모리를 더 점유하는 것은 허용하지만, 실행 중에 계속 만들고 버리는 할당은 피한다. 수천~수만 엔터티를 대상으로 표준 managed collection을 길게 유지한다.

Eager allocation

Context의 capacity hint로 Table과 Index 용량을 미리 확보한다.

Stable resident state

Primary map과 secondary bucket을 장수명으로 재사용하며 변경 이력은 보관하지 않는다.

No shrink churn

자동 축소와 반복 재구축을 피하고 삭제 슬롯을 재사용한다.

  • Primary와 unique index는 엔터티 참조를 직접 보관할 수 있다.
  • 질의마다 임시 HashSet이나 중간 List를 생성하지 않는다.
  • Reflection은 모델 구성 단계로 제한하며 행 조회 hot path에서 사용하지 않는다.
  • 결과 materialization은 호출자가 ToArray, ToList로 선택한다.
  • 메모리 paging, compression, LRU, eviction, custom allocator는 범위 밖이다.

비동기 생명주기 Persistence API async-only

초기화, import, 전체·부분 export, 물리 write 경계는 public 동기 API를 만들지 않는다. 표준 Stream이 전송 대상을 추상화하고 Task 계열이 완료·실패·취소를 표현한다.

작업 Public 형태 이유
Initialize / Import Task 외부 read와 CPU batch 처리
Full / Partial export Task Stream write와 cancellation
Input / Output transport Stream MemoryStream·FileStream·플랫폼 adapter 재사용
Memory CRUD / Query 동기 fast path 기다릴 외부 작업이 없으며 Task overhead가 불필요
byte source·sink를 별도로 재구현하지 않는다. callback 기반 SDK는 호출자 adapter 안에서 표준 Stream으로 연결하며 별도 callback overload도 제공하지 않는다.

Task는 외부 I/O 완료를 표현할 뿐 Core가 작업을 worker나 병렬 실행으로 옮기지 않는다. background 처리가 필요하면 호출자가 별도 데이터나 별도 Context로 구성하며 같은 Context에 동시에 접근하지 않는다.

Import·Export session과 session이 반환한 collection은 해당 callback이 실행되는 동안만 사용하며 보관하지 않는다.

전체 Snapshot 복구 가능한 baseline

기본 XML·JSON snapshot은 라이브러리가 판별하는 format 식별자와 호출자가 관리하는 schemaVersion을 서로 다른 값으로 기록한다. 각 row의 객체 매핑은 .NET 표준 XmlSerializer와 DataContractJsonSerializer에 위임한다. 

<odbSnapshot format="unity-odb-xml-1" schemaVersion="3">
  <entity name="Item">
    <row>
      <Code>potion</Code>
      <Id>1</Id>
      <Name xsi:nil="true" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" />
    </row>
  </entity>
</odbSnapshot>
  • 초기화는 기존 Set 객체를 비운 뒤 선택한 포맷의 row를 순서대로 파싱해 TryAdd한다.
  • Primary·Hash·Unique index는 OnModelCreating 선언에 따라 TryAdd 과정에서 다시 만든다.
  • payload에는 schema·index catalog를 중복 저장하지 않으며 entity 순서는 모델 등록 순서를 따른다.
  • 기본 importer는 자체 exporter가 기록한 고정 envelope 순서를 그대로 받으며 JSON object 재정렬은 지원하지 않는다.
  • format은 ODB가 관리하는 불투명한 식별자다. XML은 unity-odb-xml-1, JSON은 unity-odb-json-1을 사용한다.
  • schemaVersion의 기본값은 1이다. 저장되는 entity·member의 이름, type, 의미가 바뀔 때 SetSchemaVersion으로 올리고 index·capacity 변경에는 올리지 않는다.
  • 기본 importer는 현재 ModelSchemaVersion과 같은 snapshot만 받는다. 다른 버전은 사용자 정의 importer에서 구버전 DTO를 읽어 현재 entity로 변환한다.
  • XML row는 XmlSerializer와 XML serialization 특성, JSON row는 DataContractJsonSerializer와 data contract 특성을 따른다.
  • JSON은 public get·set 멤버를 기본 계약으로 삼고 null과 빈 문자열을 별도 값으로 보존한다.
  • 알 수 없는 멤버 무시와 누락 멤버의 기본값 처리는 선택한 BCL serializer의 표준 동작을 따른다.
  • Unity IL2CPP stripping에서는 엔터티 type, public 기본 생성자, 직렬화 멤버를 [Preserve] 또는 소비 프로젝트의 link.xml로 보존한다.
  • 실패와 취소는 그대로 전파하며 clear 뒤 적재된 빈 상태나 부분 초기화 상태가 남을 수 있다. rollback은 제공하지 않는다.
  • XML exporter는 재사용 buffer로 비동기 batch write하고 JSON exporter와 기본 importer는 현재 snapshot을 버퍼링한다. 다른 포맷은 importer·exporter 구현으로 교체한다.
using (var buffer = new MemoryStream())
{
    await source.CopyToAsync(buffer, 81920, cancellationToken);
    buffer.Position = 0;
    var sourceSchemaVersion = ReadAndValidateHeader(buffer);

    buffer.Position = 0;
    var items = sourceSchemaVersion switch
    {
        1 => ReadAndUpgradeV1Items(buffer),
        3 => ReadV3Items(buffer),
        _ => throw new InvalidDataException($"Unsupported schema version: {sourceSchemaVersion}")
    };

    foreach (var item in items)
    {
        if (session.TryAdd(item) == false)
            throw new InvalidDataException("Duplicate primary or unique key.");
    }
}

위 ReadAndValidateHeader·ReadAndUpgradeV1Items·ReadV3Items는 호출자가 구현하는 의사 코드다. 입력을 한 번 버퍼링하고 format을 검증한 뒤 source schemaVersion에 맞는 parser로 분기한다. session.ModelSchemaVersion은 현재 Context가 요구하는 목표 버전이므로 InitializeAsync에 별도 version 인자를 추가하지 않는다.

호출자 주도 부분 Export 변경 추적은 Core 밖

기본 exporter는 전체 DB를 기록한다. 사용자 정의 exporter는 OdbExportSession에서 필요한 Set을 요청한 뒤 row를 직접 골라 호출자가 원하는 포맷으로 기록한다.

  • UnityOdb는 revision, dirty key, journal, checkpoint, tombstone을 관리하지 않는다.
  • 무엇이 변경됐고 무엇을 저장할지는 호출자가 별도로 추적한다.
  • 병합, 재시도, 압축, 원자 게시 여부도 호출자 저장 계층의 책임이다. 압축은 표준 GZipStream을 조합한다.
  • Export가 끝날 때까지 같은 Context를 변경하지 않는 것은 호출 계약이다.
  • Core는 freeze, lock, 원자 snapshot을 제공하지 않고 live read-only collection을 exporter에 노출한다.
표준 XML·JSON 직렬화와 압축 BCL contract 우선

기본 exporter는 UTF-8 without BOM으로 기록한다. XML 입력은 XmlReader의 표준 인코딩 감지를 따르고 JSON 입력은 UTF-8을 사용하며, row 매핑은 각 BCL serializer의 기본 계약을 따른다. 

await using (var gzip = new GZipStream(destination, System.IO.Compression.CompressionLevel.Fastest, true))
    await db.ExportAsync(gzip, new OdbJsonSnapshotExporter(), cancellationToken);

await using (var gzip = new GZipStream(source, CompressionMode.Decompress, true))
    await db.InitializeAsync(gzip, new OdbJsonSnapshotImporter(), cancellationToken);

압축 여부는 importer·exporter 옵션이 아니라 전달한 Stream 조합으로 결정한다. Export 뒤 compressor를 dispose해야 footer가 완성되며 FlushAsync만으로는 충분하지 않다. 세 번째 인자 true는 호출자 소유 stream을 열어 둔다.

항목 기본 규칙
출력 인코딩 UTF-8 without BOM
입력 인코딩 XML은 XmlReader 자동 감지, JSON은 UTF-8
포맷 식별자 XML unity-odb-xml-1, JSON unity-odb-json-1
Schema 버전 기본값 1, 호출자가 SetSchemaVersion으로 변경하며 JSON에는 number로 기록
줄바꿈 문자열의 CR·LF를 XML 문자 참조 또는 JSON escape로 보존
멤버·값 변환 XmlSerializer 또는 DataContractJsonSerializer 기본 매핑
문자열 인덱스 기본 Ordinal, 필요 시 OrdinalIgnoreCase 명시
null 표현 XML은 xsi:nil, JSON은 null
출력 호출자 소유 Stream에 직접 기록

XML의 odbSnapshot·entity와 JSON의 format·schemaVersion·entities envelope는 ODB 고유 계약으로 유지한다. 객체 멤버를 텍스트로 바꾸는 범용 로직은 BCL에 맡기고 별도 scalar codec을 두지 않는다.

사용자 정의 값은 선택한 BCL serializer가 지원하는 surrogate property와 표준 특성으로 표현한다. envelope 자체가 다른 포맷은 별도 importer·exporter가 담당한다.

초기 public API와 검증 가능한 성능 기준

Public API 방향 현재 Core Runtime 기준

프로젝트 명명 규칙에 따라 first-party interface는 I... 접두사가 아니라 ...Interface 접미사를 사용한다.

입력과 출력은 .NET 표준 Stream을 사용해 MemoryStream, FileStream, 플랫폼 adapter를 그대로 받는다. 별도 byte source·sink interface는 만들지 않는다. 

public interface OdbImporterInterface
{
    Task ImportAsync(OdbImportSession session, Stream source, CancellationToken cancellationToken);
}

public interface OdbExporterInterface
{
    Task ExportAsync(OdbExportSession session, Stream destination, CancellationToken cancellationToken);
}
public abstract class OdbContext
{
    public Task InitializeAsync(
        Stream source, OdbImporterInterface importer, CancellationToken cancellationToken = default);

    public Task ExportAsync(
        Stream destination, OdbExporterInterface exporter, CancellationToken cancellationToken = default);

    protected abstract void OnModelCreating(OdbModelBuilder modelBuilder);

    protected OdbSet<TEntity, TKey> GetSet<TEntity, TKey>()
        where TEntity : class
        where TKey : notnull;
}
if (db.Items.TryFind(itemId, out var current))
    db.Items.Replace(itemId, current.WithLevel(nextLevel));

var ownerItems = db.Items.FindBy(item => item.OwnerId, ownerId);

if (db.Items.TryFindBy(item => item.Code, itemCode, out var codedItem))
    Use(codedItem);

using (var source = File.OpenRead(snapshotPath))
    await db.InitializeAsync(source, new OdbXmlSnapshotImporter(), cancellationToken);
using (var destination = File.Create(snapshotPath))
    await db.ExportAsync(destination, new OdbXmlSnapshotExporter(), cancellationToken);
입력은 현재 위치부터 끝까지 소비하고 출력은 현재 위치부터 기록하며 Core가 위치를 복원하지 않는다. 두 Stream은 호출자가 소유하므로 Core가 dispose하지 않는다. 실패한 출력은 일부 기록됐을 수 있어 원자 교체는 호출자가 담당한다.
성능 계약 속도 우선 · 과최적화 금지

목표는 극단적인 zero-allocation 엔진이 아니라, 명시적 index-backed API를 호출했는데도 전체 순회하거나 정상 사용 중 GC spike를 만드는 어처구니없는 성능 실패를 방지하는 것이다.

연산 목표 경로 계약
Primary TryFind Dictionary lookup 1회 LINQ·reflection·boxing·lock·복사 없음
Unique TryFindBy Selector catalog + Dictionary lookup 결과 materialization 없음
Hash FindBy Selector catalog + Dictionary + 기존 bucket 행 수가 아닌 결과 수에 비례
Range index Ordered seek + bucket 전체 정렬을 반복하지 않음
Partial export Custom exporter selection 요청한 Set만 순회 · row filter는 exporter 비용
Full export Dense table scan 중간 전체 string을 생성하지 않음

Steady-state 금지 항목

  • 행마다 wrapper·iterator·reflection 객체 생성
  • 인덱스 교집합마다 새 HashSet 생성
  • 명시적 index-backed API의 silent full scan
  • 부분 export에서 선택하지 않은 Set까지 강제로 순회
  • collection의 반복 resize·shrink와 대형 임시 버퍼 폐기

OdbSet의 일반 LINQ는 전체 Set을, FindBy 결과의 LINQ는 선택된 bucket만 순회한다. 표준 LINQ iterator allocation과 interface 열거의 boxing 가능성은 허용하고, OrderBy는 대상 범위를 buffer에 담아 정렬한다. Selector 식과 materialization 비용이 측정상 문제가 되면 prepared query로 분리한다.

검증과 출시 기준 Player에서 측정
Correctness

무작위 Add·Replace·Remove 후 index 결과를 기준 LINQ 결과와 비교한다.

Performance

Dictionary와 List baseline 대비 lookup, update, import, export를 측정한다.

Compatibility

깨끗한 Unity project의 Mono·IL2CPP Player에서 import부터 재복구까지 실행한다.

  • 1천, 1만, 10만 row에서 primary·unique·hash·range lookup을 측정한다.
  • cold query와 cached·prepared query를 분리 측정한다.
  • 반복 fast path의 GC allocation과 full·partial export peak를 기록한다.
  • Explain() 또는 동등한 진단에서 IndexSeek·RangeScan·FullScan을 확인한다.
  • 개발 환경은 silent FullScan을 경고하고 strict option에서는 예외로 전환할 수 있다.
  • Runtime assembly는 UnityEditor, 동적 proxy, Reflection.Emit에 의존하지 않는다.
  • Initialize의 지원하지 않는 format·불일치 schemaVersion·고정 순서 위반·key 충돌이 즉시 실패하는지 검증한다.
  • 전체·부분 export와 import 실패 전파가 호출자 계약대로 동작하는지 검증한다.
